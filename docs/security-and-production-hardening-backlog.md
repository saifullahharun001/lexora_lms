## Supporting requirements restored from the historical backlog

These are **proposed design requirements / pending verification**, except for the mandatory activation gates above and separately identified runtime evidence. They supplement the SEC entries without changing academic authority or declaring any item complete.

### SEC-18: biometric import and reconciliation

- Design a transactional import-batch and row-level reconciliation ledger. Preserve batch source identity, total/accepted/rejected/unmatched counts, failures and timestamps, with traceable student, device, class-session and course-offering mappings within the principal's department.
- Preserve the proposed historical batch states: `PENDING`, `PROCESSING`, `PARTIAL`, `COMPLETED`, `FAILED` and `CANCELLED`. These are not claims about current enums. Map their intended semantics to the existing `AttendanceImportBatch` lifecycle in [Academic Core](academic-core.md#lifecycle-and-invariants) during implementation design; do not rename existing states through documentation.
- Define duplicate detection and deterministic idempotency for repeated batches and rows. An illustrative deduplication input is student identity + device timestamp + device identity + class-session identity, scoped to the department. Final key construction, timestamp normalization and collision handling require design verification.
- Handle partial imports, retry and failure logging without duplicate acceptance. Keep unmatched students/sessions and conflicting evidence pending explicit reconciliation; address device-clock drift and timezone inconsistencies without silently assigning attendance to a different session.
- Provide department-scoped administrator reconciliation with exact object authority, required correction reasons and audit lineage. Preserve ACTIVE-session capture rules and existing correction authority; administrative reconciliation is not a bypass. Only explicitly accepted/reconciled records may feed eligibility, and the P0 production verification gate still applies.
- Apply strict source-data privacy, access and retention limits; determine the minimum necessary retained fields and retention periods. **Never store fingerprint templates.** Keep logs and queue payloads free of unnecessary biometric-source data.

Already frozen authoritative Attendance `/5` records must not be reopened, mutated, regenerated or replaced by reconciliation. The project owner confirms that the canonical Attendance `/5` rubric is current and the printed older Ordinance rubric is outdated for this purpose. This correction changes neither rubric values nor attendance calculations. Attendance marks and examination eligibility remain separate decisions.

### SEC-25: gradual database isolation evaluation

Evaluate PostgreSQL RLS gradually, starting with a reviewed inventory of high-risk department-scoped tables: enrollment/student academic records, attendance/import evidence, assessment marks/results, transcript snapshots/tokens, and sensitive file or notification records. These are candidate areas, not an approved table list or evidence of deployed policies. Preserve the narrower verified CurriculumCourse three-parent relational-integrity fix; it is not universal database isolation.

Principal-derived application scoping, `AuthGuard`, `PolicyGuard`, `@RequirePolicy()`, object authorization and safe cross-department denials remain mandatory. `x-department-id` cannot override principal scope. Proposed RLS must supplement these controls and must not create a cross-department bypass.

Before any rollout, verify trusted session/transaction context establishment, clearing and failure behavior across connection reuse, retries, jobs and transactions. Evaluate Prisma and PgBouncer or managed-pool compatibility under the selected pooling mode; do not assume session context survives transaction pooling or remains isolated when a connection is reused. Include LAW/BUS cross-department negative tests for reads, writes, forged/missing/stale context and reused connections. Public transcript verification needs an isolated minimal-read context and response; it must not inherit tenant administration privileges or broadly bypass isolation. RLS remains pending.

### SEC-16/17: complete secure file pipeline

Required production sequence: **authorization → size/quota validation → quarantine → extension/signature/MIME validation → safe filename and storage-key handling → malware scanning → controlled activation → authorized download**.

Use private object storage with signed URLs or controlled proxy access subject to current authorization, scope and expiry. Enforce per-user and per-course size/storage limits, access restrictions and audit. Define ZIP/archive safety limits for traversal, nesting and decompression abuse; isolate preview processing; review video storage, streaming access and resource limits. Failed scans, timeouts and retries retain quarantine; absence of a successful trusted scan must never imply CLEAN or permit activation.

Isolated MinIO/ClamAV verification, the database scan ledger and idle-worker tests remain bounded foundations. They do not prove actionable production jobs, complete pipeline atomicity, authorized upload/download or production enablement. SEC-17 worker sequencing cannot weaken SEC-16's P0 gate.

### SEC-19: asynchronous notification delivery

Design asynchronous queues/workers so large recipient expansion occurs outside synchronous API operations. Preserve safe event payloads, template rendering, recipient snapshots, retry and delivery-attempt tracking, deterministic deduplication, critical-preference protection, department/recipient isolation and privacy-safe audit. Keep logical notifications separate from channel delivery attempts and verify failures/retries do not duplicate delivery or cross scope.

BullMQ/Redis and RabbitMQ are historical technology options, not approved mandatory dependencies. Broker/adapter selection and real EMAIL/PUSH production delivery remain pending; existing in-app/API and placeholder delivery rows do not prove real transport success.

### SEC-20/21/22: production decisions and optional expansion

Production acceptance requires explicit decisions and verification for reproducible deployment packaging, HTTPS/domain/proxy security, secret management, automated protected backups and tested restores, structured sanitized JSON logging, centralized error monitoring, uptime/resource monitoring, queue and authentication-security monitoring, incident response and rollback. Preserve audit privacy and avoid logging secrets, tokens, biometric payloads or confidential marks.

Define a PostgreSQL connection-budget strategy covering application instances, workers and operational headroom. Evaluate direct connections, PgBouncer or managed pooling against the actual workload; test Prisma behavior under the selected pooling mode, including transaction semantics, retries and any proposed RLS context. RLS context isolation and pooling compatibility must be verified before adopting the combination.

Docker/Docker Compose or equivalent reproducible packaging are options; adequate reproducibility and rollback are required, while adopting Docker is not. PgBouncer or managed pooling and expanded APM/metrics are P2 options when capacity or observability needs justify them. Essential logging, monitoring and connection safety cannot be deferred merely because a particular P2 tool has not been selected. Technology choices, retention/alert thresholds, connection budgets and implementation scheduling still require architectural and operational review.

## Non-negotiable rules

- No super-admin or cross-department bypass. Principal-derived scope wins over x-department-id. AuthGuard, PolicyGuard, @RequirePolicy(), object authorization, Teacher assigned-course and Student own-resource restrictions remain mandatory.
- Preserve safe-not-found behavior and all negative-security evidence. UI visibility is never authorization.
- Preserve authoritative source locks, exact versions/provenance and append-only amendment history. Missing/invalid source evidence fails closed.
- Chairman /60 approval, automatic /40 derivation, complete-result Chairman finalisation and Controller publication are distinct. Enforce separate component passes; no client-supplied authoritative marks.
- GPA/CGPA recalculation is controlled; transcript snapshots remain immutable. Hash verification tokens, enforce expiry/revocation, return minimal public responses.
- Attendance capture is active-window bound; attendance/eligibility overrides require reason, actor and audit. Current generated Attendance /5 is irreversibly frozen through ordinary workflows.
- Preserve notification tenant/recipient privacy, critical preferences and deduplicated delivery.
- Required protected audits commit atomically with the academic action; audit failure must not leave successful unaudited academic evidence.
- Retain and neutralize immutable runtime academic evidence. Remove/revoke temporary authentication authority without deleting protected records or recording secrets.
